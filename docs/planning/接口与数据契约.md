# 智能规划接口与数据契约 v1

日期：2026-10-16。demo已实现需求会话、首次生成、修改、追加、预览、提交与撤销；当前边界见 [第六七轮说明](第6-7轮-整合与验收.md)。旧 `plan()/PlanResult` 保持原语义，新响应使用 `schemaVersion: "planning.v1"`。生成要求有效日期和至少一个点位，尚不支持相对日草案。

## 1. 公共约定

- 所有写请求同源 JSON，服务端验证 Origin、身份归属、长度和参数；后端从 Cookie 获取用户或游客身份。不得接受客户端 `userId` 作为归属依据。
- 成功：`{schemaVersion, requestId, data}`；失败：`{schemaVersion, requestId, error:{code,message,retryable,details}}`。
- `requestId` 用于追踪；`idempotencyKey` 用于写请求防重复。相同归属/端点/key/请求体返回相同操作结果，key 相同但请求体不同返回 409。有效期覆盖工作任务生命周期。
- 时间用 ISO 完整日期时间和偏移，另传 IANA `timeZone`；前端日期按目的地显示，不使用服务器时区。“16号”等仅在区间内唯一时解析，保存原文依据。
- 金额用整数最小货币单位和货币码；时长用整数分钟，未知为 null，不用 0 代替未知。
- ID 均由后端生成或从目录解析。日期范围、人数、时长等服务端作范围校验；本文件不是直接传给供应商的 JSON Schema。
- 工作流/模型输出严格做 Schema 和业务校验；只允许已注册工具。模型不能提供权威 ID、版本号、校验通过状态或操作成功结果。

## 2. 需求状态

### PlanningContext

```json
{
  "lineId": "fanhua-shanghai",
  "selectedPoiIds": ["sh-ip-01", "sh-sp-01"],
  "dateRange": {"startDate": "2026-11-01", "endDate": "2026-11-02"},
  "timeZone": "Asia/Shanghai",
  "recommendationId": null
}
```

允许日期为空以采集需求，但无法确定具体日期时只能生成日期待确认的草案。空点位可根据目录生成选择建议，不静默替用户确认；不能满足最低规划数据条件时返回 `NEEDS_CORE_CONTEXT`，不是强迫回答偏好问题。

### Requirement

每项包含：`id, key, value, strength, scope, source, evidence, state`。

- `key` 使用受控维度：`party / pace / mobility / rest / wake / departure / dayEnd / transport / shopping / meals / budget / queue / freeTime / poiDepth / mustVisit / exclude / fixedEvent / scheduleLock`。
- `value` 按 key 校验，不能任意字符串混入可执行内容。party 含人数/年龄段可空；mobility 含步速与单段步行容忍；rest 含间隔与时长；poiDepth 逐点设置；fixedEvent 含类型、位置、时间、预订状态。
- `strength`: `hard / soft`；unknown 由 state 表达，不是另一种强度。
- `scope`: `{type:trip|day|poi|event, targetId:null|string}`；day 使用完整日期。
- `source`: `user_option / user_text / profile / policy_default / tool`。
- `evidence`: `{messageId:null|string, answerId:null|string, quote:null|string, factId:null|string}`。原话不伪造。
- `state`: `confirmed / inferred / assumed / unknown / superseded`。confirmed 的用户偏好与 tool 事实分开解释；画像推断不能升级为已确认硬约束。

冲突优先级：本次明确需求 > 已确认行程约束 > 已保存明确偏好 > 画像推断 > 政策默认。相同优先级的显式相互矛盾要求返回冲突或追问，不单靠排序覆盖。明确撤销/替换可覆盖原项，保存 superseded；局部例外不覆盖全程习惯。

`scheduleLock` 是 hard 需求，其 value 为 `{lockedDates:[],lockedItemIds:[],baselineVersion}`。基准快照由后端从用户当前行程读取并固定，不接受客户端/模型自报基准内容；锁日约束该日全部安排的语义字段（地点、顺序、起止、交通方式、游览深度），不因重新生成内部 ID 而失效。“其他尽量不变”用软 preservation 策略，不误记为锁定。

### Question / Keyword

`Question = {id, templateId, category, priority, reason, fields, options, skippable:true, relatedRequirementIds}`。

- priority: `critical / useful / optional`；fields 定义字段 ID、类型、标签、允许值和是否可留空。所有问题可整题跳过。
- options: `{id,label,value}` 数组；前端用 `questionId/optionId` 提交，不依赖模型文案反向解析。
- templateId 必须来自 [问题库](../../skills/travel-itinerary-planner/references/questions.md)。模型只选择模板、填受控标签和 reason；不决定字段类型或可执行 UI。
- `Keyword = {id,label,insertText,source,relatedRequirementIds}`。点击仅插入文本，提交后才生效；不从已删除标签恢复需求。

服务端维护 `intakeRevision`、已问/已跳过问题、普通追问轮数与 `generationRequested`。模型提出问题不等于已展示一轮；重试不增加轮数。若解析不清，不将软偏好自动变成硬约束。

## 3. 端点

| 方法与路径 | 请求 | 响应 data |
|---|---|---|
| POST `/api/planning/sessions` | `{context,text,answers,idempotencyKey}` | 需求快照及首轮分析 |
| POST `/api/planning/sessions/:id/intake` | `{baseIntakeRevision,text,answers,skippedQuestionIds,action,idempotencyKey}` | 新需求修订及下一轮问题 |
| POST `/api/itineraries` | `{planningSessionId,intakeRevision,idempotencyKey}` | 创建生成 job，不立即覆盖其他行程 |
| GET `/api/planning/jobs/:id` | 无 | `{state,phase,result,error}` |
| GET `/api/itineraries/:id` | 无 | 当前已提交快照 |
| GET `/api/itineraries/:id/additions?baseVersion=N` | 无 | 当前版本追加候选；无副作用 |
| POST `/api/itineraries/:id/revisions` | `{baseVersion,baseIntakeRevision,text,operations,selectedCandidateIds,idempotencyKey}` | 创建联合试排 job；不能同时提供矛盾的 text/operations |
| POST `/api/itineraries/:id/commits` | `{previewId,baseVersion,idempotencyKey}` | 原子应用预览，返回新快照 |
| POST `/api/itineraries/:id/undo` | `{baseVersion,targetVersion,idempotencyKey}` | 基于历史快照创建更大的新版本 |
| GET `/api/itineraries/:id/services?kind=tickets或restaurants&poiId=...` | 当前行程景点 | 携程只读结果与安全跳转链接 |

intake 的 action 为 `continue / skip / generate`。generate 合并当前答案并停止普通追问；不默许放宽已确认硬约束。首次生成状态通过 job 返回，不在请求超时后悄悄生成重复对象。

`answers=[{questionId,optionIds,values}]`；values 对应 fields 中的字段 ID，选项和字段值冲突返回 422。已跳过项可用后续明确答案覆盖。

第五轮补充：首屏模板在 `src/planning/question-bank.mjs` 与服务端共享，首次创建可提交 `q:<templateId>:0` 的选项答案；动态追问继续使用服务端实际返回的 questionId。每次最多60条结构化答案，支持逐点深度；首屏不依赖模型才能展示。

`mobility.value` 新增 walkingLevel=low/moderate/high、maxDailyWalkMinutes；数字上限均为地点间交通步行，不含景点内。`meals.value` 支持 preference、lunchStart/lunchEnd（开始时间窗）、durationMinutes。

需求快照响应：`{planningSessionId,intakeRevision,requirements,nextQuestions,suggestedKeywords,unresolved,generationReadiness}`。

generationReadiness 为 `ready / provisional / needs_core_context`。不使用含糊的布尔值暗示事实齐全。

jobs：`state=queued|running|succeeded|failed|cancelled`；phase 为 `analyzing|fetching|scheduling|validating|repairing|complete`。result 为判别联合：首次有草案 `{kind:"itinerary",itinerary}`；修改完成 `{kind:"preview",preview}`；无法形成首份草案 `{kind:"negotiation",conflicts,choices,unresolved}`。任务成功产生冲突预览/协商结果仍是 succeeded，约束失败使用 validation/conflicts 表达，工具或协议故障才是 job failed。阶段由服务端实际执行设置。轮询退避，取消接口留到实现阶段按需求增补。

首次生成通过或暂定草案保存版本 1；已知冲突以 partial 草案保存并禁止伪装为通过，空结果可返回 negotiating 结果而不创建行程。模型 API 失败不能包装为真实 AI 成功。

IP 推荐独立端点 `POST /api/recommendations/ip`，返回 `{recommendationId,items:[{lineId,reason,keywordCandidates}]}`；其实现由推荐负责人负责。共享 LLM 调用标注 `purpose`，不共享 messages/history。跨功能只传有来源的数据，不直接转发系统提示或整段聊天。

## 4. 行程结果与事实来源

`Itinerary = {id,version,planningSessionId,intakeRevision,context,validation,days,requirements,unresolved,assumptions,conflicts,createdAt}`。

`validation = {status:passed|provisional|failed, checkedAt, factSnapshotId, checks, violations}`，只能由校验器生成。

- passed：在声明的数据来源、交通估算模型及已知条件下通过检查；不是实时交通/履约保证。
- provisional：存在影响可行性的关键未知项，只能标暂定；如未知营业时间、机场或活动场次。
- failed：已知硬约束违反；仅作为 partial 草案或协商依据，不允许作为已通过行程提交。
- `checks` 每项 `{code,status:pass|fail|unknown,relatedIds}`；不因字段缺失跳过检查后称为通过。

`Day = {date,startAt,endAt,items,totals,unscheduledPoiIds}`。items 按时间排序：

第五轮新增：Day 可带 `walkingCoverage:"between_places_only"`、`mealWindows`；totals.walkMinutes 仅统计 travel 的 walkMinutes。visit 可带 planningPaddingMinutes（0至4），取整后时长=源停留时长+padding；meal 带 mealId/label/preserveClock。fixed_event 不取整。所有占用取实际排程值，前端的“约”不改变校验结果。

```text
{id,type:visit|travel|meal|rest|wait|buffer|fixed_event|free,
 startAt,endAt,poiId:null|string,eventId:null|string,
 fromId:null|string,toId:null|string,transportMode:null|string,
 durationMinutes,walkMinutes:null|number,
 factIds:[],certainty:observed|estimated|unknown}
```

totals 分别统计 visit/travel/meal/rest/wait/buffer/free 和总占用，不能将交通块与景点 `legMinutes` 双计。准备起床时间单独表示，不混入游览开始；每日总占用和各项起止一致，逐日检查截止。

`Fact = {id,kind,value,source,provider,fetchedAt,validFor,certainty}`。

- 交通 key 至少含 from/to、方式、出发时间或适用时间段；有方向性。开放事实包含日期/时区、多个时段、闭馆与最晚入场；预约事实含场次/名额查询状态，不等于用户已预订。
- 手工库、工具实查、缓存与距离估算分别标注；不伪造 fetchedAt 或来源。来源未知的 `openHours` 文本需保留不确定性。
- 无数据时 null；有明确政策默认时记录 assumptions 和 policy 版本。默认步速、准备时间、缓冲等为后端配置，不由模型临时创造。

## 5. 修改、追加和提交

操作为判别联合，按 type 校验字段：

| type | 字段 |
|---|---|
| add_poi | poiId, date:null|string, afterItemId:null|string |
| remove_poi | poiId |
| move_poi | poiId, date, afterItemId:null|string |
| set_depth | poiId, depth:deep|normal|quick |
| set_requirement | requirementId:null|string, key,value,strength,scope；证据由后端附加 |
| lock_day / unlock_day | date；后端生成或解除scheduleLock，基准来自当前版本 |

自然语言操作每项附 `evidence:{quote:本次原话逐字片段}`；指代模糊可返回 `{kind:"clarification",questions,message}` 的job结果，不创建预览。首屏可显式提交engineMode=rules，仅应用结构化选项，未解析文字保留未知；不是AI调用失败后的自动降级。

模型提出的操作先校验 ID/授权/字段，再排程。移除已有 mustVisit 需要用户明确解除对应约束；单纯模型提出移除不算授权。

`Preview = {id,baseVersion,baseIntakeRevision,expiresAt,factSnapshotId,operations,preserve,proposedItinerary,diff,validation,requiresChoices}`。

`preserve = {lockedDates:[],lockedItemIds:[],baselineVersion,minimizeOtherChanges:true|false}`；硬锁来源必须对应用户证据与 scheduleLock 需求，基准快照留在服务端。schedule/validate/preview/commit 全链传递并检查；校验器对锁定区域与基准逐项比较。后续修改仍保留有效锁，直到用户明确解除或替换；不得只写在模型 explanation 中。

diff 包含 added/removed/moved/depthChanged/timeChanged/transportChanged、每日增量和不受影响部分。requiresChoices 是具体取舍及受影响约束，不能只给泛泛“是否确认”。failed 的预览不能 commit；用户选择后重新试排。provisional 允许提交为显著标注的草案。

`Addition = {candidateId,poiId,baseVersion,reasonCodes,reason,suggestedDate,afterItemId,beforeItemId,incrementalMinutes,incrementalWalkMinutes,validationStatus,bookingState,factSnapshotId,expiresAt}`。

reasonCodes 为受控原因，如 `ip_related / explicit_interest / profile_interest / low_detour / available_window`。增量必须来自实际插入试排，未知为 null；源于旧启发式时只能标估算建议，不标 validated。是否预约不由模型猜测。

推荐绑定版本、需求修订和事实快照，多选必须整体试排。commits 校验归属、baseVersion、需求修订、TTL 和依赖数据有效性；变更则返回 stale 并重新预览，事务内 compare-and-swap。撤销保留审计历史，恢复前重验事实；失败则返回冲突而不倒退版本号。

## 6. 工具边界（计划注册，不表示已存在）

工具均返回 `{ok,data,facts,error}`。只读工具不能修改正式行程。供应商的工具参数 JSON Schema 在第四轮按实际 API 支持范围生成，并同时进行本地校验。

| 名称 | 输入核心字段 | 输出核心内容 |
|---|---|---|
| resolve_pois | lineId, queries/poiIds | 候选点、歧义、规范 ID；查无不可创建假点 |
| get_poi_facts | poiIds, dates, timeZone | 开放、停留区间、活动/预约信息及缺失项 |
| get_travel_matrix | locations, modes, departureWindows | 定向交通、步行、时间适用范围及来源 |
| schedule_itinerary | context, requirements, candidateOrder, facts, preserve | 时间轴、未排项目、计算失败；不写库 |
| validate_itinerary | draft, requirements, factSnapshotId,preserve,baselineSnapshot | 逐项检查、锁定区域对比、violations、未知项；基准由后端注入，不接受模型自报 passed |
| evaluate_additions | itineraryId,baseVersion,candidatePoiIds,requirements | 分别插入试排并排序的候选；多选仍需 schedule |

编排器主动执行最后校验。携程 MCP 经适配器提供已核验能力，门票查询不等同于交通、开放或实际预订；本流程不自动购买。

## 7. 错误与兼容

400 请求格式；401/404 未授权或资源不可访问；409 `STALE_VERSION / STALE_INTAKE / STALE_PREVIEW / IDEMPOTENCY_CONFLICT`；422 参数或已知约束冲突；429 分功能限流；502 模型/工具协议错误；503 未配置供应商/不可用；504 总时限超时。后台任务失败在 job.error 返回同一错误结构。

约束无解不是模型服务故障，优先以 negotiating/preview 的结构化 conflicts 表达。错误详情不包含密钥、邮箱、Cookie 或模型内部推理。

旧页面适配：新结果投影为旧 `days[].items[]` 的 visit 项及 arrive/leave/duration/legMinutes，仅用于旧组件显示；来源标签、非游览块和校验状态需要新组件。新界面不把 `under70` 当作必须追加，不用旧 `impossible` 作为证明。旧“两类点各选一个”限制在本期新规划中解除，允许只选书中地点；零点位须明确选择生成建议或补点，不能空行程显示成功。
